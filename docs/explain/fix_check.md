# fix_check: The result of testing the finding's suggested fix

## What it means

The evidence records whether the suggested fix diff stopped the attack and whether your tests still passed. The outcome is one of `fix_verified`, `fix_check_partial` (the original, variants and benign verdicts all passed, and either no test command was given or an applicable decoding variant still shows the effect), `fix_rejected` or `fix_unverified`. It names the diff by SHA-256 and applies only to that exact diff. It never changes the finding's status.

The check reports three verdicts, each `pass`, `fail`, `inconclusive` or `not_run`, plus the project `tests` result:

- `original`: the base input showed the effect on the original copy and none on the fixed copy.
- `variants`: every other scoring variant was blocked on the fixed copy.
- `benign`: the benign input behaved normally on both copies.

All three run to the end, so one failing verdict does not hide the others. If the base input shows no effect on the original copy there is no baseline, and `variants` and `benign` stay `not_run`. Because a failing fix now runs every input instead of stopping at the first unblocked one, it uses more container runs. The budget formula is unchanged. The JSON summary keeps a `regression` field for older consumers. It is derived from the three verdicts and is not a separate check.

The detail string has 12 parts: `fix_check: outcome= original= variants= benign= tests= inputs=k/n decoding=b/a/t diff_sha256= reason= blocker= variant_set_sha256= variant_generator_version=`. A check with no generated set ends after `blocker=`. Details from before this change (6, 7 or 9 parts, with a single `regression=`) still parse, but they are marked legacy and never count as verified. Rerun the fix check to get a current result.

`blocker` is set only when the outcome is `fix_unverified`, and it comes from the reason token alone, by an exact list (no prefix matching). `environment` means the sandbox, image or prepared copy could not be built, could not be read on the host, or changed during the check (the report says the environment could not be rebuilt). `harness` means the adapter was refused or could not be built, or the harness failed or gave no verdict on the original copy (the report says the harness could not be built). `none` is every other case, including refusals caused by repository or diff content (for example `snapshot_symlink`, `snapshot_too_large`, `tree_too_large`, or `diff_does_not_apply` for a diff that patches both a file and a path inside it, such as `x.py` and `x.py/y.py`) and any unknown token. A blocker is never a verdict that the fix failed or did not work: the check could not judge the fix.

The fixed copy runs the patched code, so the fix itself can end a run there: exit non-zero (for example `os._exit`), hang until the timeout, or print no, an invalid or a duplicate verdict line. The harness runner also reports `error=true` when the child running the checked code times out, exits non-zero, returns a missing or invalid result, or changes the evidence while it runs. When the original copy gave a verdict for that input, any of these on the fixed copy (an `error=true` run counts only when it shows no effect) means the input is not counted as blocked: the verdict in progress becomes `inconclusive` with reason `fixed_copy_no_verdict` and blocker `none`, and the check goes on with the remaining inputs and the benign control. A Python exception raised by the checked code (`raised=true`) is different: with no effect it counts as blocked, and the benign control catches a fix that always raises. A later failing verdict still makes the outcome `fix_rejected`. Once two fixed-copy runs in one check have ended by timeout (the checked code's 30-second limit, the runner's own hard limit, or the container timeout), no further input runs on either copy. The verdict in progress and every later one become `inconclusive` with reason `fixed_copy_no_verdict` and blocker `none`. An effect already seen on the fixed copy still makes the outcome `fix_rejected`. This keeps patched code that hangs on every input from using a timeout per input. Only a missing baseline (the base input shows no effect on the original copy), a failure on the original copy, two fixed-copy timeouts, an exhausted budget or a passed deadline stops the check early. If the prepared copies or the image identity change after the run, a result that is not negative is replaced by `fix_unverified` (`snapshot_changed` or `image_identity_changed`); an observed `fix_rejected` is kept, without a binding.

A positive result also needs a clean reason (`fix_verified` has `reason=none`; `fix_check_partial` has `none` or `decoding_variant_not_blocked`; any other detail does not parse) and must name the current variant set: `variant_set_sha256` and `variant_generator_version` equal to today's set for the finding's class. The `vettalon fix check` receipt has no finding, so it accepts today's set of any class. A receipt made with an older or different set is shown as `fix_unverified` with reason `variant_set_outdated` (blocker `none`); rerun the fix check. The same binding rule (complete binding for this exact detail and diff, test command recorded exactly when tests ran) applies to the `vettalon fix check` receipt and to the finding label.

The per-verdict fields (`original`, `variants`, `benign`, `tests`, and the decoding counts) in the MCP `phases` and in the SARIF `vettalon.fix_check` property are the raw measured verdicts. The top-level `outcome` is authoritative: it may be downgraded to `fix_unverified` for a binding problem or an outdated variant set even when every verdict shows `pass`.

The checks use a fixed variant set (`variants/1`) for command injection, path traversal and SQL injection. The set comes only from the class: no random source and no model. The base input is first. Every scoring input must show the effect on the original copy and none on the fixed copy. The receipt field `variant_set` records `generator_version`, `sha256`, `total`, `ids_not_blocked` (every scoring id that was not blocked, in set order), `decoding_ids_not_blocked` and `decoding_ids_not_applicable`. The evidence detail adds `decoding=<blocked>/<applicable>/<total>` for inputs that need decoding (percent-encoded `../` on paths). A decoding input is applicable only when the original copy showed the effect, and blocked only when it is applicable and the fixed copy showed none. A variant that never triggers on the original, such as `%2e%2e/` against `os.path.join`, is not applicable and is not counted as blocked. Those inputs are executed and listed. They are not part of `inputs=<blocked>/<total>`. An applicable decoding variant that still shows the effect caps a verified fix at `fix_check_partial`; it does not by itself reject the fix. Details without `decoding=` parse as 0/0/0.

Node target mode also supports SSRF (CWE-918) under `variants-node/1`: 16
loopback variants, 14 scored, with IPv6-loopback and userinfo as non-scoring probes.
The effect is an HTTP request line or TLS ClientHello at the protected runner's
listener. For SSRF, benign success means the public URL reached a network-layer
failure in the offline sandbox, as reported by the target's error/cause chain.
The fixed copy must preserve a recognized network error code such as `EAI_AGAIN`
or `ENOTFOUND`. A normal return or policy exception without that signal makes the
benign verdict `inconclusive`, reason `ssrf_benign_unconfirmed` (no blocker), so a
block-everything patch is never verified. Listener setup failure is
`ssrf_listener_unavailable`, an environment blocker. Python targets and scan-time
SSRF oracles remain unsupported. See `vettalon explain node_exec`.

When the original, variants and benign verdicts pass and `decoding_blocked` is below `decoding_applicable`, the outcome is at most `fix_check_partial` with reason `decoding_variant_not_blocked`. A failing or inconclusive project test still wins. A decoding variant with no effect on the original stays informational and does not change the outcome. The evidence detail adds `variant_set_sha256` and `variant_generator_version` when a generated set ran, and `check_sha256` covers those tokens. Older details that omit them still parse. Policy `vettalon-fix-check-v4` and harness `vettalon-three-class-oracle-v3` are current; older policy and harness strings still read, but they are not a complete binding.

A pass means only that no effect was observed for this revision, these inputs and these variants. It does not prove the fix is complete. It is also not proof against an adversarial diff: the inputs are fixed and known, so a diff that special-cases them can pass while the bug stays. For SQL injection, a target function may write to the SQLite database during the run (for example enabling WAL or inserting a log row). The evidence check ignores the database file's change time. It still requires the same file (device and inode) with the same type and permissions, and it re-reads the fixture tables: the secret row and the `items` row must be unchanged. A database that was replaced, renamed, had its permissions left changed, or lost or changed either fixture row makes that input inconclusive, not blocked. A change to the database that is undone before the checked code exits is not detected. The per-run marker reaches the harness runner on stdin only, and the adapter and project code run in a child process of the runner. The runner is PID 1 of its container and makes itself non-dumpable before any checked code starts, so checked code cannot read its memory or outlive its cleanup. After checked code ran, the runner checks each evidence file's content and whether it was renamed, replaced or had its permissions changed, even if the change was undone (for the SQL injection database, only changes still in place, as above). Code in the checked copy also runs as the same user as the harness, so it can still detect the harness or alter evidence files in ways the runner's integrity check does not catch.

Known limit: the receipt is not tamper-evident by itself. Anyone who can edit the report can write a consistent v4 detail and `fix_context_v1` binding that displays as verified; the hashes show consistency, not who wrote them. Sign and verify receipts with `vettalon receipt sign` / `vettalon receipt verify` (being added in v0.8), or keep reports in a store you trust.

`vettalon reproduce` and the scan-time PoC still use the single base input. In a `--poc` scan each fix check gets its own container budget, sized the same way as `vettalon fix check` (2N+4 plus a margin, capped at 48). It does not draw the 20-run PoC counter. A full check uses 16/18 container runs for command injection, 18/20 for path traversal and 14/16 for SQL injection (the first number has no project tests). A caller that passes a budget too small for the whole check (both sides of every input, two benign controls, plus two test runs when a command is set) skips it before it starts with reason `poc_budget_exhausted`. A claim that fails during the check uses that same reason. The scan's 20-run counter is for PoCs only; when it skips a PoC the scan is incomplete with [poc_budget_exhausted](poc_budget_exhausted.md), not `time_budget_exhausted`. One scan starts at most five harness fix checks. Later suggested fixes are `fix_unverified` with reason `fix_check_cap_reached`, and the scan is incomplete with [fix_check_cap_reached](fix_check_cap_reached.md). If the scan deadline passes before the next input, the check stops with `time_budget_exhausted` and the scan is incomplete. The human-readable report shows decoding counts only when `decoding_total` is greater than 0. The label that names a decoding variant still showing the effect is used only when the outcome is `fix_check_partial`. A detail with reason `decoding_variant_not_blocked` parses only when original, variants and benign passed and `decoding_blocked` is below `decoding_applicable`.

## Why you see it

A `--poc` scan checked the suggested fix of a High or above finding, or you ran `vettalon fix check`. Only command injection, path traversal and SQL injection findings have a harness for this.

## What to do

Confirm the hash matches the fix you plan to apply. For a full check, add `--fix-test-command "<your test command>"`.
